# P3-01 T03-R01～R03 安全回退作業規格（草案｜假資料演練完成，正式演練未完成）

> 僅供獨立開發分支驗收；此文件不是執行回退或正式部署的授權。正式 Supabase 與會員資料不可因閱讀同步問題而自動覆蓋、清除或猜測歸屬。

## 一、風險與既有基準

- 開發基準 main：`01f9924da8c106992f2490f59d90750293c6f817`。
- 舊版 `assets/cloud.js` 仍掃描無 UID 範圍的 `wb:last:*`，可能把本機 A 的紀錄當作 B 的紀錄同步。
- 因此直接回復上列 main、直接解除新閱讀資料管理層，或重啟舊版 `wb:mig:yu-split-1` 搬移程序，都 **不是安全回退**。
- 手機舊有 33 項通過紀錄並不代表本版或回退版已通過回歸。

## 二、緊急操作的安全目標

1. 優先停止閱讀紀錄同步寫入，不影響公開小說閱讀。
2. 保留新的 `wb:v2:member:<uid>:`、`wb:v2:guest:` 及未歸屬 `wb:last:*` 等歷史本機資料。
3. 不在無法驗證身分時從任何其他會員空間取值。
4. 不執行舊版一次性全域搬移，也不以 `wb:mig:yu-split-1` 判斷資料已完全轉換。
5. 避免修改正式 `reading_progress` 內容；資料修復另行查證並授權。
6. 緊急時可停用閱讀同步功能；登入／收藏／留言等服務不應擴大改動範圍。

## 三、受控安全回退方案（待建置與演練）

- 不回退至 `01f9924` 的舊閱讀同步實作。
- 基於已通過驗收的修正版建立後續緊急版，保留 `reading-store.js` 和 `_layouts/default.html` 的載入順序。
- 若必須停用同步，只阻斷 `assets/cloud.js` 的閱讀紀錄 `sync(A)` 入口；不得修改收藏、留言或資料庫授權規則。
- 所有已經發出的網路請求不保證能取消；需以實際 JWT、RLS 和回傳狀態確認邊界。
- 應先在測試裝置證明 A／B／訪客資料仍各自隔離、舊資料不變、網路失敗不誤報已同步。
- 應保留每次操作前後的 Git commit、部署版本、測試結果及復原紀錄，由站長另行核准合併與正式部署。
